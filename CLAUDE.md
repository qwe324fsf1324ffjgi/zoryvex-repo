Founder is non-technical. One recommendation, not a menu, unless the decision is legally/financially irreversible. Do every safe code/test/Git/doc/IaC action yourself; never ask the founder to edit a file.

## Hard boundaries

- Providers: AWS, GitHub, Claude, Vercel Domains (registrar/DNS only, no Vercel project), Paystack. MCPs: exactly Magic/21st (one capability), GitHub, Filesystem, Context7, Playwright — never a sixth.
- **No Amazon Cognito, ever**, for application auth — see docs/adr/0001-no-cognito-passwordless-email-auth.md. This overrides any older preserved-prompt text that still names Cognito (see docs/DECISIONS.md).
- No AWS root session, no IAM users, no static AWS keys. IAM Identity Center for the human; GitHub Actions OIDC for CI.
- No Route 53, no Vercel hosting project, no ECS/EKS/EC2/RDS/Aurora/ALB/NAT Gateway/Redis/provisioned concurrency/always-on compute, no default VPC.
- No Terraform apply, DNS change, live Paystack plan, live checkout, or data destruction without a plan, a diff, a tested rollback, and explicit founder approval.
- Never print, log, commit, or send a secret (incl. via MCP). Redact account IDs, keys, tokens, addresses, bank info, and private candidate evidence from all output.
- Never claim completion from a compile/build alone — only from a passed acceptance test.
- Never `git reset --hard`, `git clean -fd`, force push, rewrite history, bulk-delete, or do an unplanned broad refactor. Scan for secrets and inspect deletions/renames before every commit.
- Smallest reversible change. Read + diff before editing.

## Loop / goal discipline (full detail: docs/LOOP_RUNBOOK.md)

- 12 cumulative `/goal` turns per phase (tracked in `.zoryvex/state.json`, which overrides Claude's own resettable counter). 6 checks per read-only polling `/loop` — never used for building.
- Same failure twice → stop with `REPEATED FAILURE STOP`, no third attempt. Intermittent test → run 3x, unexplained failure = `FLAKY - NOT PASSED`, never masked.
- Before writing, every phase/resume: verify working directory, repo identity, branch/upstream, merge state, last good commit, working-tree changes, dependency lock, config names, baseline tests. Never continue from detached HEAD, an unresolved Git op, an unexplained deletion, or the wrong project.
- Context unreliable → stop, persist state, clear goal, compact/resume, run the Universal resume prompt, continue only after `RESUME CHECK PASSED`.
- Claude Pro usage pause is not a failure: checkpoint, `USAGE PAUSED - RESUME SAME PHASE`, resume same phase after reset — never switch to an API key/Console credits/another account without explicit approval.

## Fixed product (do not change without founder decision)

Proof-first hiring platform, four launch tracks only (cloud engineering, DevOps/platform, cloud-security/DevSecOps, MLOps/ML platform — MLOps recorded 2026-08-27 to match what the code has shipped since Phase 7; see docs/DECISIONS.md). **Graded tasks are retired as a verification method** (founder decision 2026-09-06, ADR 0005): a published brief marked against a published rubric is solvable from the brief by a language model, so the mark said nothing about the person while ranking above a certification bound to their own address. No claim type maps to `graded_task`, the type system excludes it, and `isVerified` refuses it retrospectively. The catalogue still exists, inert; its deletion is outstanding and recorded in ADR 0005. This supersedes ADR 0004's sequencing, which ordered multi-cloud work around writing more tasks. The instruction ADR 0004 served — not only AWS talent — is now met by certification verification across four issuers: AWS, Google Cloud, the Linux Foundation (Kubernetes exams) and IBM Professional Certification (HashiCorp). **Microsoft and Azure certifications cannot be verified at all**: Microsoft left Credly in 2024 and Microsoft Learn publishes no credential bound to the holder's address. Never offer one as verifiable. **The `aws_cloud` label is now "Cloud engineering"** (founder decision 2026-09-09: "For the roles that says AWS engineer. Make it cloud engineer. Because the app is not restricted to only aws"). The identifier `aws_cloud` is deliberately unchanged: it is the stored value on every existing candidate and role, and renaming it would be a data migration to change a word on a screen. The label is what anybody reads and it is the only thing that was wrong. **Two routes were removed on 2026-09-09** (founder instructions, "remove upload file feature" and "remove ask someone to confirm this"), and they belong together. Uploading a file to a claim, and asking a colleague to confirm one, were the only two things on the evidence page that could not be checked against a source the candidate does not control: a file is theirs, and a colleague is somebody they chose. Both are gone from the product. What remains is what Zoryvex checks itself, which is the whole argument it sells: a certification confirmed with the body that issued it, and control of a public repository proven by a one-time code published in a public gist. The upload/scan/download pipeline and the three peer endpoints still exist in the codebase, unreachable from any screen; deleting their S3 bucket, GuardDuty malware protection and API routes is a Terraform destroy and stays `NOT AUTHORIZED BY FOUNDER` until approved, recorded the same way ADR 0005 records the graded-task catalogue. `peer_verified` stays in the strength ladder because records already holding it earned it honestly; nothing new can attain it. Candidates free; employers pay. Primary offer: `proof_hiring_kit_v1`, NGN 95,000 one-time (raised from 29,000, founder-approved 2026-08-30), works with zero marketplace candidates, no invented people/evidence/outcomes. AI may summarize/explain, never make the final hiring call, infer protected traits, score faces, or silently reject. Founding prices fixed (Scout 800,000 / Team 1,400,000 / Partner 2,400,000 monthly; first 5 orgs only, reduced from 25 on 2026-09-02; no annual plans). Standard prices, for everyone after those 5, are also fixed (Scout 1,200,000 / Team 2,000,000 / Partner 4,000,000 monthly). Raised 2026-09-09 on the founder instruction "lowest price even for founder should be 800000", the fourth raise. The floor was the only figure given and could not be applied alone: founding Scout was 300,000 while founding Team was already 800,000, so lifting the floor would have put two tiers at one price. **The ladder is compressed, not scaled**, because the ceiling is not the founder's to set: 4,000,000 is the most any single charge can be and still leave room for its own renewal inside Paystack's 8,000,000 lifetime limit, and scaling the old ladder to a 800,000 floor would have put standard Partner near 10,700,000 — above the entire account limit, the same failure the 10,000,000 price caused on 2026-09-04. Earlier figures (founding 79,000/229,000/599,000 then 150,000/400,000/900,000 then 300,000/800,000/1,800,000; standard 250,000/700,000/5,000,000 then 500,000/1,400,000/4,000,000, and Partner briefly at 10,000,000) are history, in docs/DECISIONS.md. Founding discounts are 33% on Scout, 30% on Team and 40% on Partner, a tighter spread than before and deliberately so. Copy should not make a claim about the spacing of the three tiers either way. The two sets still interleave, the same way: founding Scout (800,000) is below standard Scout (1,200,000), which is below founding Team (1,400,000), so a founding Team buyer pays more than a standard Scout buyer. **The Kit is deliberately unchanged at 95,000**: the instruction was about what a founding member pays for a subscription, and the Kit is the one-time primary offer. **Standard Partner can be sold at most once**: the Paystack Starter Business lifetime collection limit is 8,000,000 account-wide, so 4,000,000 leaves room for one payment and one renewal, shared with every other sale. Lifting that needs a Registered Business (CAC, `NOT AUTHORIZED BY FOUNDER`). See docs/PRODUCT_SPEC.md. Founding members keep their price for the life of the subscription. Both price sets are the same product — founding buys a lower price, never extra features. Paystack disclosure, exact wording, before every paid redirect and on support: "Payments are securely processed by Paystack under our business name, Abba's Solutions."

## Voice & design standards (durable — recheck on every user-facing change)

The product must read and look like it was made by a careful human product team, never like an AI wrote or designed it. This is a standing bar, not a one-time cleanup — apply it to every new page, string, or component, not just at review time.

- No AI-cliché vocabulary: "seamless", "leverage", "empower", "unlock your potential", "elevate", "cutting-edge", "revolutionize", "dive into", "unleash", "robust solution", "tailored to your needs", "state-of-the-art", "holistic", "frictionless", "supercharge", "effortless(ly)", "world-class", "best-in-class", "game-changer", "whether you're... or...", "it's important to note", "in today's [x] world". If a sentence needs one of these to sound impressive, cut the sentence and say the concrete fact instead.
- Em dashes are the single most recognizable AI-writing tell — real human copy uses them rarely. In visible prose (marketing copy, UI microcopy, toasts, error/empty states), default to a period, comma, or colon instead; never stack two em dashes as a parenthetical aside in one sentence. `<title>` tags and short compact labels ("Page — Site", "Item — price") are a normal, unrelated web convention and don't need to change. For a compact inline metadata separator in a UI row (e.g. `action · target`, `plan · status`), use a middle dot `·`, not an em dash — reads as designed UI, not written prose.
- Keep the existing restrained visual system: the ink-950/warm-50/emerald-accent palette and `system-ui` font stack (see `apps/web/app/globals.css`'s own comment — chosen specifically to avoid the generic AI-SaaS blue-purple-gradient-plus-Inter look), border-based `Card` (not shadow/gradient), no glassmorphism/backdrop-blur, no gradient hero backgrounds or floating 3D blob art, no generic icon-in-a-circle feature grids. Extend this system; don't introduce a competing one.
- Every claim on the site must stay true to what's actually built (see Fixed product, Trust & Safety, and docs/COMMERCIAL_RUNBOOK.md) — never let a copy-quality pass introduce a claim that outruns reality.
- Before shipping new user-facing text or a new component, read it back and ask: would a sharp human copywriter or designer have written/built exactly this, unprompted? If it reads like an assistant's first draft, revise it before it ships.

## v4.5 commercial addendum (full text: docs/COMMERCIAL_RUNBOOK.md)

Optimize durable cash flow and retained revenue, never vanity counts or fabricated traction. One primary launch offer (the Kit); no recurring marketplace push before 5 real opted-in matches. Track the real commercial scorecard (docs/COMMERCIAL_SCORECARD.md), not registrations alone. "High demand" / "low competition" / "initial demand validated" are internal operational gates with hard evidence thresholds — never public claims until met. One product-led sharing loop per side (employer, candidate), consent-gated, privacy-minimized, no paid referrals, no dark patterns. Zero paid ads at launch; no new paid service without a cost memo + approval; Bedrock off unless proven materially useful within a cost cap; scale from measured demand only. A passing build or one payment is never proof of success — if unit economics turn negative or trust/privacy issues appear, stop growth changes and repair the smallest reversible thing first. Never weaken the legal gate to make money.
