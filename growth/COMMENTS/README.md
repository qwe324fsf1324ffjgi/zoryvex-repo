# Comments

## Read this before using any of them

The original brief asked for 500 comments. This file contains **120**, and I
want to be straight about why rather than quietly deliver a smaller number.

A pre-written comment is only useful if it answers something someone actually
said. Past roughly a hundred, you are no longer writing answers, you are
writing variations, and variations posted across a platform are indistinguishable
from a comment-spam operation. The project's own commercial runbook forbids
dark patterns and vanity-count growth. Five hundred pre-written comments
deployed at any real rate would be exactly that, and for a company selling
verification, being caught doing it is a fatal story, not an embarrassing one.

So: 120 distinct comments, organised by the situation they answer, with a rule
about volume at the end. If you want the remaining 380 anyway, say so and I
will write them. This is a recommendation, not a refusal.

---

## The rule that governs all of them

**Never post a comment that does not answer the specific thing that was
said.** If none of these fits the post in front of you, the correct number of
comments is zero.

Also:

- Never lead with the product. Lead with the answer
- Never post the same comment twice on the same platform
- Never comment on a post about a named person's rejection or firing
- Never comment under someone's job-seeking post to advertise anything
- If you would not send it to one person, do not post it to a thousand

# A · Someone says hiring is broken (1–15)

1. The part I keep getting stuck on is that nothing on a CV has been checked
   by anyone at the moment you read it. Not the dates, not the titles. We've
   just stopped noticing.

2. Most fixes here are about reading CVs faster. Almost none are about
   checking whether the thing you're reading is accurate.

3. Worth separating two problems: too many applicants, and no way to tell
   which ones are accurate. Screening tools solve the first and make the
   second worse.

4. The interview is doing work the CV should have done. Half of it goes on
   establishing whether the document was true.

5. Broken how, though? Slow, or wrong? They need opposite fixes and most tools
   pick speed.

6. Filtering harder doesn't help when you're filtering on unverified inputs.
   You just get faster at the wrong answer.

7. The thing that changed isn't candidate quality. It's that producing a
   convincing document got much cheaper.

8. Every hiring process I've seen assumes the CV is roughly true and then
   spends the whole process finding out.

9. "We get 800 applicants" and "we can't find anyone" are usually the same
   company saying the same thing twice.

10. A process that can be passed by someone who isn't the person on the CV
    wasn't verifying. It was reading.

11. The honest version is that we outsourced judgment to a document nobody
    audits.

12. Most of the pain is in the gap between what a CV asserts and what anyone
    confirmed. That gap is where all the wasted time lives.

13. Referrals work for one reason: somebody who is accountable vouched. That's
    verification with extra steps and a small network.

14. If the screening signal is unverified, adding AI to it scales the error,
    not the accuracy.

15. Fair to ask what would actually count as fixed. My answer: the interview
    stops being an audit.

# B · Someone says certifications are meaningless (16–30)

16. Depends entirely on whether the issuer publishes a record bound to you. A
    certificate you can verify and a PDF of one are different objects.

17. The problem was never that certificates are weak. It's that the real one
    and the screenshot look identical.

18. A certificate isn't proof you can do the work. It's proof a specific body
    tested you on specific material and will confirm it. Much smaller claim,
    much more useful.

19. Some can be checked with the issuer, some can't. That distinction predicts
    usefulness better than which certificate it is.

20. AWS, Google Cloud, the Linux Foundation and IBM publish verification
    addresses. Microsoft doesn't any more, since leaving Credly in 2024.

21. Worth knowing before you book an exam: is there an address where somebody
    else can confirm it.

22. "Anyone can pass it in a weekend" and "nobody can confirm you passed it"
    are separate complaints. The second one is fixable.

23. A weekend certificate isn't worthless. It's just not evidence on its own.

24. Paired with a repository you can prove you control, a certificate stops
    being a claim and starts being a data point.

25. The gap is between holding a credential and anyone being able to check
    that you hold it.

26. If your answer is "I have the certificate", the next question is "where
    can I confirm that". Having a good answer there is most of the value.

27. Employers discounting certificates is rational given how easy a PDF is.
    They're discounting the document, not the knowledge.

28. There's a version of this complaint that's really about the exam and a
    version that's really about verification. They have different answers.

29. Renewal matters too. A verification address that shows a lapsed credential
    is more honest than one that shows nothing.

30. The useful question isn't "is this certificate respected". It's "can
    somebody else confirm I have it without asking me".

# C · Someone asks how to stand out as a junior (31–45)

31. Two things do most of the work: a certification from an issuer that
    publishes a verification address, and a public repository where the
    commits are credited to you.

32. Make the repository public, not a fork, and not empty. Those three
    conditions rule out most of what people link to.

33. One real project you can explain beats six tutorial clones. Somebody will
    ask you a question about it.

34. Commits credited to your account matter more than the code being
    impressive. It has to be yours before it can be good.

35. Write up what broke and how you found it. That reads as experience in a
    way a feature list doesn't.

36. If you can't prove you control it, don't link it. A repo you can't
    establish ownership of is worse than no link.

37. Pick a certification you can verify. Studying something uncheckable is the
    same effort for less signal.

38. The advice "build a portfolio" usually skips the part that matters:
    anybody has to be able to confirm it's yours.

39. Fixing a real issue in someone else's project is stronger evidence than a
    fresh repository nobody uses.

40. A README that explains the decision you made and the one you rejected does
    more than a demo video.

41. Don't pad. A short CV with two checkable things beats a long one with
    none.

42. The honest advantage a junior has is being verifiable. Someone with ten
    years has claims nobody will ever check.

43. Deployed and running beats a screenshot, but only if the repository behind
    it is public and credited to you.

44. Answering questions in public, accurately, is evidence. It's slow and it
    compounds.

45. Whatever you build, make sure a stranger can establish it's yours in under
    a minute without asking you.

# D · Someone says AI screening is unfair (46–60)

46. The specific harm is usually that somebody was removed and nobody can say
    why. That's an explainability problem before it's a bias problem.

47. Worth distinguishing a model that summarises from a model that decides.
    The second one is the one people are describing.

48. If the model receives a name and a photo, it can infer things nobody
    authorised. The fix is to not send them.

49. "Unbiased AI" isn't a claim anyone can support. "Explainable, and a person
    decides" is.

50. The test I'd apply: if the model is switched off, does the process still
    work. If not, it's deciding.

51. A score with no stated factors isn't a screening tool, it's a refusal with
    a number attached.

52. Appeal is the missing piece. A rejection you can't question isn't a
    decision, it's an outcome.

53. Speed is the sales pitch and the harm at the same time. It's fast because
    nobody looks.

54. Structured evidence in, explainable factors out, human decides. That's not
    exciting and it's the only defensible shape.

55. The model shouldn't be ranking people. It can summarise evidence people
    then read.

56. Every "AI-powered hiring" pitch I've read describes the throughput and not
    the recourse.

57. If it can't say which evidence produced the conclusion, it isn't
    explaining. It's asserting.

58. Protected traits leak through proxies. Not sending the fields at all is
    cruder and much harder to get wrong.

59. Fairness audits after the fact don't help the person already filtered out
    in March.

60. The question to ask a vendor: can your model reject someone. If yes, the
    rest of the answer doesn't matter much.

# E · Someone asks about verification or background checks (61–75)

61. Background checks and skill verification are different things. One
    confirms who you are, the other confirms what you can do.

62. The useful property is whether the source is controlled by the person
    being checked. A file they uploaded isn't.

63. A reference the candidate nominated is a reference. Useful, but not
    independent.

64. Proving repository control takes about a minute: publish a one-time string
    in a public gist, then the repo gets read. No account access needed.

65. Checking with the issuer is slower than accepting a screenshot and it's
    the only version that means anything.

66. The thing to look for is what happens when the check fails. If the answer
    is "it's shown anyway, unmarked", it isn't a check.

67. Upstream being unavailable and the claim being false have to be different
    outcomes. Collapsing them punishes people for GitHub having a bad day.

68. A verification that can't be repeated later isn't a verification, it's a
    timestamp.

69. Worth asking: what does this system do with a claim it cannot check. Say
    so, or quietly display it?

70. Scanning an uploaded document proves it isn't malware. That's the whole
    guarantee.

71. Most "verified" badges mean somebody clicked a link. Ask what was on the
    other end.

72. The 2026 Verizon DBIR documents people being hired at real companies with
    stolen identities. That's the ceiling of what unverified hiring allows.

73. Verification narrows what can be faked. It doesn't eliminate it, and
    anyone claiming otherwise is selling something.

74. A credential bound to an address the issuer publishes is the cheapest real
    verification available today.

75. The reason this is hard is that the useful sources are few and the
    convenient ones are worthless.

# F · Someone posts about being rejected or ghosted (76–85)

**Handle with care. Most of the time the right response is nothing.**

76. That's a rough one. For what it's worth, silence after a final round is
    usually a process failure, not a verdict on you.

77. Worth asking for the feedback in writing. Some places will give it and
    almost nobody asks.

78. No advice, just: the volume of applications means the signal-to-noise is
    bad in both directions right now.

79. If you got to a final round, the evidence held up. That's worth separating
    from the outcome.

80. Ghosting is about their process, not your work. Small comfort and still
    true.

81. If you want a second pair of eyes on what you sent, happy to look. No
    pitch.

82. One thing that sometimes helps: make sure everything you listed can be
    confirmed by someone who isn't you. It removes one whole category of
    doubt.

83. Sorry. That's genuinely demoralising and the standard advice doesn't
    really touch it.

84. Not much to add except that it's a numbers problem on their side and it
    reads as a personal one on yours.

85. Take a few days. The advice will still be there and it's better received
    when you're not raw.

# G · Someone is building something similar (86–95)

86. The decision that cost us most was refusing uploaded files as evidence. It
    removed the easiest path and it was the right call.

87. Watch out for verification methods a language model can pass. We retired
    graded tasks for exactly that reason.

88. Rate limits will be your wall. Unauthenticated GitHub is 60 requests an
    hour per IP, and one verification spends three.

89. Separate "upstream unavailable" from "check failed" in your types, not
    just your copy. They diverge everywhere.

90. Entitlement derivation belongs in exactly one function. Every place it's
    re-derived is a place it drifts.

91. Verify the webhook signature and dedupe on a hash of the raw body, not the
    event id. Providers resend more than you'd think.

92. Decide early what you show a user whose claim you cannot check. That answer
    shapes the whole product.

93. If the check is optional, it's decorative. Ours gates what employers can
    see.

94. The hardest part isn't the verification. It's the copy that explains
    honestly what you did and didn't check.

95. Fail closed everywhere. A verification system that degrades open is worse
    than none, because people trust it.

# H · Someone asks what Zoryvex is (96–105)

**Only use these when directly asked.**

96. We check a small number of claims against sources the candidate doesn't
    control, and show employers only what we actually checked.

97. Two methods: a certification confirmed with the body that issued it, and
    control of a public repository proven by a one-time code in a public gist.

98. Candidates pay nothing. Employers pay. That's deliberate: who pays decides
    what the product optimises for.

99. Employers see "Candidate a1b2c3" and the proof. They get contact details
    only after the candidate says yes.

100. Four kinds of work: cloud engineering, DevOps and platform, cloud security
     and DevSecOps, MLOps. Narrow on purpose.

101. We don't accept uploaded files as evidence and we removed peer
     confirmation. Both were removable for the same reason.

102. No customer logos on our site because we don't have customers yet. Felt
     like the wrong thing for a verification company to fake.

103. The AI can summarise evidence. It cannot decide, and it never receives a
     name or a photo.

104. Anything we can't check, we say we can't check, at the form rather than
     afterwards.

105. Happy to answer specifics. It's a narrow product and I'd rather describe
     the limits than the ambition.

# I · Technical threads: AWS, Kubernetes, DevOps (106–120)

**Comment as a practitioner. Do not mention the product at all in these.**

106. The failure mode nobody documents is the one where the upstream returns
     403 and your code treats it as a negative result.

107. Reserved concurrency on every function or one runaway loop eats the whole
     account pool. Learned that the expensive way.

108. On-demand DynamoDB plus conditional writes covers more than people expect
     before you need anything cleverer.

109. A dedupe key derived from the payload hash survives providers that reuse
     event ids. An event id doesn't.

110. Feature flags read per invocation, never cached, is the difference between
     a thirty-second mitigation and a deploy.

111. A partial parameter write deletes the keys it omits. That one cost us four
     days of drift.

112. Never conclude a deploy worked from its exit code. Check the running
     version endpoint.

113. Retrying a `terraform apply` on a flaky connection is how a failed apply
     becomes a partial one.

114. PITR restores to a new table. It's a cutover, not an undo, and that
     changes your incident plan.

115. Non-fatal catches hide missing environment variables perfectly. `requireEnv`
     throws before the thing you're watching ever runs.

116. A test that reads your actual Terraform and asserts the env vars exist
     catches a class of bug no unit test will.

117. Mutation testing is the only way I've found to prove a guard is load-bearing
     rather than decorative.

118. OAC plus a private bucket, not a public bucket with a policy. There's no
     reason to run the second one any more.

119. If your authorizer defaults to allow while you build it, it will ship that
     way. Default deny from the first commit.

120. Idempotency keys on payment initiation, stored with the attempt in one
     write. Two writes means a window.

## Volume

**Maximum five comments a day across all platforms.** More than that and the
pattern is visible regardless of quality.

**Never** run these through automation. Every one is written to answer
something specific, and a scheduler cannot tell whether it does.

## What a good comment does

It is worth reading by someone who never clicks through. If it only makes
sense as a route to Zoryvex, it is an advertisement in disguise, and the
audience for a verification product is exactly the audience that notices.
